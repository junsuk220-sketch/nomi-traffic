# 교통음성알림 헌법 V1

적용 범위: **Naver 교통음성알림**. Google · TMAP · Memory Engine은 이 헌법의 대상이 아니다.
확정일: 2026-09-12 · 상태: V1 (개정은 제15원칙에 따른다)

이 문서는 개발 설명서가 아니다. **무엇을 해도 되고 무엇을 하면 안 되는지를 판단하는 기준점**이다.
구현 방법·숫자·문자열·클래스 이름은 본문에 두지 않는다. 부록 A(Policy) · B(Parameter)에 둔다.

---

## 제0장. 목적

이 앱의 목표는 기능이 많은 앱이 아니다. **작지만 매우 안정적인 핵심 위에 기능을 하나씩 올리는 것**이다.

헌법이 지키려는 것은 다음 아홉 가지다.

1. 동일한 상황에서 예측 가능한 결과
2. 잘못된 교통정보를 말하지 않음
3. 중복 음성 최소화
4. 현재 Journey와 관계없는 정보 차단
5. 상태의 명확한 소유권
6. 기능 간 간섭 최소화
7. 문제 발생 시 원인 추적 가능
8. 테스트를 통한 재현 가능
9. 새로운 기능의 안전한 확장

**이 헌법은 전면 재설계를 요구하지 않는다.** 현재 구조(관측 → 파싱 → 판단 → 문장 → 발화)를 보존하고,
그 위에서 앞으로의 변경을 통제하는 것이 목적이다.

## 제1장. 핵심 원칙 (15)

### 제1원칙 — 결정의 일관성
동일한 유효 관찰 sequence가 들어오면 가능한 한 동일한 판단과 음성 sequence가 나와야 한다.
이벤트 도착 순서나 우연한 타이밍에 따라 결과가 달라지는 구조를 최소화한다.
**이 원칙은 다른 모든 원칙보다 우선한다.** 기능·정확도·똑똑함보다 앞선다.

### 제2원칙 — 현재 Journey 중심
앱은 사용자가 시작한 현재 Journey를 기준으로 판단한다.
현재 Journey와 관계없는 교통정보는 현재 안내에 사용하지 않는다.
단, **현재 Journey 안에서의 후보 교체는 명확한 근거가 있을 경우 허용한다.**
Journey가 없으면 아무 말도 하지 않는다.

### 제3원칙 — Observer와 Judge 분리
알림과 화면 접근성은 **관찰자**다. 관찰자가 각각 독립적으로 최종 판단을 내리지 않는다.
`Observation → Parsing → Decision → Speech → TTS`의 책임을 분리한다.

### 제4원칙 — 관찰 정보의 출처 보존
판단에 필요한 정보(출처 · 관찰 시각 · 정류장 귀속 · 관찰 내용)는 **판단 단계까지 보존한다.**
중간 계층에서 정보가 사라져 추측으로 판단하게 만들지 않는다.

### 제5원칙 — 불확실하면 말하지 않는다
교통정보를 확실하게 식별할 수 없다면 잘못된 정보를 말하지 않는다. 잘못된 안내보다 침묵이 낫다.
단, **무한 침묵을 방지하는 정책을 함께 둔다**(부록 A).

### 제6원칙 — 하나의 판단에는 하나의 Judge
같은 종류의 판단을 여러 계층에서 중복 수행하지 않는다. 하나의 결정에는 명확한 최종 판단 주체가 있어야 한다.

### 제7원칙 — 하나의 상태에는 하나의 Owner
동일한 사실을 여러 클래스가 각각 별도의 상태로 관리하지 않는다.
상태의 생성 · 변경 · 조회 · 초기화 책임이 명확해야 한다.

### 제8원칙 — Parser는 추출만 한다
Parser는 관찰된 정보를 구조화한다. 말할지 말지, 어떤 후보를 고를지 같은 **정책 판단은 하지 않는다.**

### 제9원칙 — Dedup에는 생명주기가 있다
중복 방지 정보는 영구 누적되지 않는다. Journey 또는 해당 기능의 생명주기에 따라 생성되고 초기화된다.

### 제10원칙 — 기능 간 간섭 금지
새 기능이 기존 기능의 상태나 실행을 불필요하게 막지 않는다.
한 기능의 보호 로직이 다른 기능을 차단한다면 **그 이유가 헌법적으로 설명 가능해야 한다.**
설명할 수 없는 차단은 위반이다.

### 제11원칙 — 침묵도 설명 가능해야 한다
음성이 나오지 않았다면 개발 단계에서 그 이유를 추적할 수 있어야 한다.
최소한 다음을 구분할 수 있어야 한다: 현재 Journey 아님 · 정보 부족 · 정류장 불일치 · 중복 ·
아직 발화 단계 아님 · 최신 정보 대기 · 후보 밖 정보 · 다른 정책에 의한 억제.

### 제12원칙 — 판단은 재현 가능해야 한다
핵심 판단 로직은 Android UI · 실시간 서비스와 분리하여 테스트할 수 있어야 한다.
관찰 sequence를 입력하면 동일한 판단 결과를 재현할 수 있어야 한다.

### 제13원칙 — 기능은 독립적으로 확장한다
새 기능은 기존 기능의 상태를 편의상 재사용하지 않고 자신의 책임과 상태를 갖는다.
기존 기능을 수정해야 한다면 그 이유와 영향 범위를 설명할 수 있어야 한다.

### 제14원칙 — 기존 기능을 함부로 깨뜨리지 않는다
변경 전에 영향 범위를 확인하고, 자동 테스트와 실기기 테스트를 거친다.
현재 정상 동작하는 기능은 보호 대상이다.

### 제15원칙 — 헌법은 구현보다 오래 산다
구현 방법은 변경될 수 있다. 핵심 원칙은 쉽게 변경하지 않는다.
**새 기능이 필요하다는 이유만으로 헌법을 개정하지 않는다.** 헌법 자체가 틀렸다는 충분한 근거가 있을 때만 개정한다.

## 제2장. 아키텍처 책임 원칙

### 2-1. 다섯 계층과 계약

| 계층 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| Observer | 플랫폼에서 관찰을 만들어 전달 | 의미 판정, 발화 여부 결정, 다른 기능의 실행 순서 결정 |
| Parser | 관찰을 구조화 | 후보 선택, 정책 판단, 상태 변경 |
| Judge | 의미 확정 · 대상 선정 · 발화 여부와 **이유** 결정 | 문장 만들기, TTS, 플랫폼 접근 |
| Speech | 확정된 결정을 한국어 문장으로 | 판단, 억제 |
| Speaker | 실제 발화 | 판단, 중복 방지 |

### 2-2. 관찰(Observation)의 최소 형태
관찰은 최소한 **출처 · 관찰 시각 · 정류장 귀속(가능한 경우) · 관찰 내용**을 갖는다(제4원칙).
이 중 무엇이 빠졌는지 판단 계층이 알 수 있어야 한다. 빠진 것을 추측으로 채우지 않는다.

### 2-3. 관찰의 유효성과 의미의 구분
- **유효성** 판정(예: 화면이 꺼져 있어 화면 관찰이 성립하지 않음)은 어댑터의 책임이다.
- **의미** 판정(이 차가 그 차인가, 지금 말할 때인가)은 Judge의 책임이다.
- 유효하지 않은 관찰은 Judge에 전달하지 않는다. 유효한 관찰을 어댑터가 해석하지 않는다.

### 2-4. 출처 간 충돌 해소
둘 이상의 출처가 서로 다른 사실을 말할 때의 해소 규칙은 **한 곳에만** 존재한다.
규칙은 고정 서열이 아니라 `유효성 → 신선도 → 기본 출처` 순서로 정의한다(구체 정책은 부록 A).

### 2-5. Judge의 반환
Judge는 결정과 **이유**를 함께 반환한다. 발화하지 않기로 한 결정도 이유를 갖는다(제11원칙).

### 2-6. 순수성
Judge와 Parser는 플랫폼 서비스에 의존하지 않는다. 이 성질은 제12원칙의 전제이며 **후퇴시키지 않는다.**

## 제3장. 상태와 생명주기 원칙

### 3-1. Journey
- Journey는 **하나만** 존재한다. 시작과 종료는 각각 정의된 지점에서만 일어난다.
- Journey의 정체성은 화면의 라벨이 아니다. 라벨과 알림은 Journey의 **증거**다.
- Journey 종료 판정이 **하나의 Observer에만** 의존하지 않도록 한다. 하나의 관찰 경로가 끊겨도 끝난 Journey가 계속 살아 있어서는 안 된다.
- Journey 단위 상태는 Journey와 함께 생성되고 함께 사라진다. **개별 초기화를 사람이 기억해야 하는 구조를 만들지 않는다.**

### 3-2. 후보 집합
- 현재 Journey의 후보 집합(같은 정류장의 대체 노선 등)은 **Journey가 소유한다.**
- 후보 편입은 **귀속이 확인된 관찰**에서만 일어난다. 확인 수단이 없으면 편입하지 않는다.
- 후보 집합 안에서의 대상 교체는 허용한다. 집합 밖으로의 이동은 Journey 변경이며 사용자 행동으로만 일어난다.

### 3-3. 상태 소유권 등록
새 상태를 만들 때 다음 네 가지를 문서화한다: **누가 만들고 · 누가 바꾸고 · 누가 읽고 · 언제 사라지는가.**
네 가지를 쓸 수 없는 상태는 만들지 않는다.

### 3-4. 같은 사실의 중복 표현 금지
같은 사실을 두 개 이상의 상태가 각자 표현하지 않는다. 파생값이 필요하면 소유자에게 물어본다.

### 3-5. Dedup
중복 방지 상태도 소유자와 생명주기를 갖는다. 앱 수명 동안 누적되는 집합을 두지 않는다(제9원칙).

### 3-6. 시계
시간 판단에 쓰는 시각은 한 종류만 쓴다. 기준이 다른 시간을 같은 필드에 담지 않는다.

## 제4장. 음성 안내 원칙

### 4-1. 단일 경로
한국어 문장 생성은 한 곳에서, 실제 발화는 한 곳에서 한다. 우회 경로를 만들지 않는다.

### 4-2. 발화의 근거
발화는 Judge의 결정 결과로만 일어난다. Observer와 Parser는 직접 말하지 않는다.

### 4-3. 중복 금지
같은 의미의 안내는 한 번만 말한다. **"같은 의미"는 자유 문자열이 아니라 종류와 키로 정의한다.**

### 4-4. 침묵
- 확실하지 않으면 말하지 않는다(제5원칙).
- **모든 침묵 규칙에는 상한이 있어야 한다.** 상한에 닿으면 가장 최신의 유효한 관찰을 채택하고 그 사실을 기록한다.
- 침묵은 기본값이 아니다. 침묵이 길어지는 것은 그 자체로 결함이다.

### 4-5. 설명 가능성
발화하지 않은 결정은 이유와 함께 기록한다. 기록이 같은 이유를 접을 때에도 **얼마나 오래 침묵했는지**를 잃지 않는다.

### 4-6. 문장을 만들 수 없을 때
문장을 만들 수 없으면 중복 방지 칸을 소모하지 않는다.

### 4-7. 정책의 위치
어떤 단계에서 무엇을 말하는지, 문구가 어떻게 되는지는 **정책**이다(부록 A).
정책 변경은 헌법 개정이 아니다. 반대로 정책을 근거로 헌법을 우회하지 않는다.

## 제5장. 기능 확장 원칙

### 5-1. 새 기능 체크리스트
새 기능을 추가할 때 다음 일곱 가지에 답할 수 있어야 한다. 답할 수 없으면 아직 추가하지 않는다.

1. 이 변경은 헌법을 위반하지 않는가?
2. 기존 기능의 상태를 침범하지 않는가?
3. 다른 기능의 판단에 영향을 주지 않는가?
4. 동일한 입력에서 동일한 결과가 나오는가?
5. 문제가 생겼을 때 이유를 추적할 수 있는가?
6. 이 기능의 상태는 언제 사라지는가?
7. 이 기능이 침묵할 때 그 이유가 구분되는가?

### 5-2. 칸 분리
기능은 칸으로 나눈다. 한 칸을 고치려고 다른 칸을 열지 않는다.
칸 사이의 영향은 **명시된 계약(공개된 하나의 경로)**을 통해서만 발생한다.

### 5-3. 새 상태보다 순수 함수
새 동작은 가능하면 상태 없는 계산으로 추가한다. 새 상태를 만드는 것은 마지막 수단이다.
(근거: 상태 하나가 추가되면 기존 상태들의 서로 다른 수명과 곱해진다.)

### 5-4. 확장 전 정리
새 플랫폼·새 안내 종류를 추가하기 **전에** 이벤트 종류 표현과 라우팅 중복을 정리한다.
정리하지 않은 채 확장하면 비용이 기능 수의 제곱으로 늘어난다.

### 5-5. 하나의 변경, 하나의 목적
한 번의 변경은 하나의 목적만 갖는다. 겸사겸사 고치지 않는다.

# 부록 A — Policy (변경 가능, 헌법 아님)

현재 확정된 정책이며, **이번 헌법 확정 작업에서 변경하지 않았다.**

**A-1. 버스 대기 안내 정책** — `docs/BUS_WAIT_CONSTITUTION.md`를 이 헌법 제4장의 하위 규격으로 편입한다.
그 문서는 실기기로 검증된 유일한 칸이며, 폐기하거나 다시 쓰지 않는다.

- 단계 안내: 10분 → 5분 → 2분 → 곧 도착 (각 단계 한 번)
- 같은 차 추적 중 마지막 발화 후 일정 시간 내 중간 단계 생략, 곧 도착은 항상 발화
- 추적 차가 바뀌면 그 한 번은 간격을 무시
- 승차 정류장 부근 이전에는 다음 차 한 대를 함께 안내, 이후에는 추적 차만

**A-2. 출처 정책** — 알림 ETA를 주 입력, 화면 시트를 보조로 본다. 화면이 꺼진 동안 화면 관찰은 성립하지 않는다.
잠금 상태에서도 알림만으로 단계 안내가 나와야 한다.
※ 이 정책은 문서화되어 있으나 **현재 구현에 반영되어 있지 않다**(부록 D, D-1 참조).

**A-3. 침묵 정책** — 출처가 엇갈리는 동안은 추적 대상을 유지하고 말하지 않는다.
단 유예에는 상한이 있어야 하며, 상한 도달 시 최신 유효 관찰을 채택하고 기록한다(제4장 4-4).
※ 현재 상한이 없다(부록 D, D-10 참조).

**A-4. 지하철 · 환승 · 하차 정책** — 빠른 환승/하차 칸 안내는 승차 지점 도착 확인 이후에만 발화한다.
하차 준비는 정류장 단위로 한 번 발화한다. 문구는 정책이며 개정 대상이 아니다.

**A-5. 첫 안내 브리핑 정책** — Journey 시작 시 첫 탑승 수단에 대해 한 줄 브리핑을 한다. Journey 하나당 한 번이다.

# 부록 C — 개발 및 테스트 절차

```
문제 발생 → 재현 → 로그 확인 → 문제 계층 확인 → 헌법 위반 여부 확인
        → 영향 범위 분석 → 변경 범위 최소화 → 테스트 작성/수정
        → 코드 수정 → 자동 테스트 → 실기기 테스트 → 결과 확인 → 다음 작업
```

**C-1.** 한 번에 하나의 목적만 수정한다.
**C-2.** 규칙이 틀렸다면 **문장(헌법 또는 정책)을 먼저 고친다.** 예외 패치를 코드에 먼저 넣지 않는다.
**C-3.** 판단 계층 테스트가 빨간 상태에서 실기기 패치를 먼저 하지 않는다.
**C-4.** 실기기에서 재현되지 않은 현상은 원인을 확정하지 않는다.
**C-5.** 증상만 보고 새 규칙을 추가하지 않는다. 규칙이 늘어나는 수정보다 정보가 늘어나는 수정을 우선한다.
**C-6.** 침묵 방향의 변경은 반드시 상한과 함께 넣는다. 침묵은 신고되지 않는 결함이다.
